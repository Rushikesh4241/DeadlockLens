Deadlock Prevention Lab • Coffman Conditions

Examine the 4 required conditions for deadlock and eliminate them via protocol simulations
Condition 1

Mutual Exclusion

At least one resource must be held in a non-shareable mode. Only one process can use the resource at any given time.

Elimination: Spooling & Virtualization. Requests are queued to a shared daemon instead of locking physical hardware.
Virtualize Resources
Condition 2 • Implemented

Hold & Wait

A process holds at least one resource and is waiting to acquire additional resources held by other processes.

Elimination: All-or-Nothing Protocol. Blocked processes release all held resources and atomically request their full claim.
Eliminate Hold & Wait
Condition 3

No Preemption

Resources cannot be forcibly confiscated from a process; they can only be released voluntarily after completion.

Elimination: Force Preemption. If a process holding resources requests one that is unavailable, its current resources are preempted.
Enable Preemption
Condition 4 • Implemented

Circular Wait

A closed chain of processes exists such that each process holds at least one resource needed by the next process in the chain.

Elimination: Linear Resource Ordering (A < B < C...). A process holding type k may only request types ≥ k.
Enforce Resource Order

Protocol Trade-Off Analysis:
  • Lower Resource Utilization: Resources are allocated in advance and held unused until the process finishes; blocked processes release all held assets.
  • Starvation Vulnerability: Processes requiring large numbers of resources may wait indefinitely while smaller processes continuously grab available units.
  • Rollback Overhead: Releasing resources mid-execution requires checkpointing or re-running computations from the beginning.

Theoretical Foundations & Algorithms

1. Banker's Safety Algorithm

Devised by Edsger Dijkstra, the Banker's algorithm tests for safety by simulating the allocation of predetermined maximum possible amounts of all resources.

1. Let Work = Available, and Finish[i] = false for all i.
2. Find an i such that: Finish[i] == false ∧ Need[i] ≤ Work.
   If found: Work = Work + Allocation[i]; Finish[i] = true; repeat scan.
3. If Finish[i] == true for all i, then system is SAFE.

2. Resource-Request Algorithm

Governs whether a dynamic request can be immediately granted without risking future deadlock.

1. If Request[i] > Need[i] → ERROR (Maximum claim exceeded).
2. If Request[i] > Available → MUST WAIT (Insufficient resources).
3. Tentatively simulate:
   Available = Available − Request[i]
   Allocation[i] = Allocation[i] + Request[i]
   Need[i] = Need[i] − Request[i]
4. Run Safety Algorithm: if SAFE → COMMIT; else → ROLLBACK & DENY.

3. Multi-Instance Deadlock Detection & WFG

1. Work = Available; Finish[i] = (Allocation[i] == 0).
2. Find i such that Finish[i] == false ∧ Request[i] ≤ Work.
   If found: Work = Work + Allocation[i]; Finish[i] = true.
3. Deadlocked set = { i | Finish[i] == false }.
4. WFG Edge: Pi → Pj if ∃ r: Request[i][r] > Work_final[r] ∧ Allocation[j][r] > 0.

Operating Systems Deadlock Glossary

Safe State
A state is safe if there exists at least one sequence ⟨P0, P1, ... Pn-1⟩ such that each Pi's remaining need can be satisfied by current Work + all preceding allocations.
Unsafe State
A state where no safe execution sequence exists. An unsafe state is not necessarily deadlocked, but deadlock cannot be guaranteed to be prevented.
Deadlock
A situation where two or more processes are unable to proceed because each is waiting for the other to release resources.
Wait-For Graph (WFG)
A directed graph derived from a Resource Allocation Graph. A cycle in a single-instance WFG indicates deadlock; in multi-instance systems it indicates circular dependency.
Starvation
Indefinite postponement of a process because other processes with higher priority or smaller claims continually acquire requested resources.
Resource Preemption
Temporarily reclaiming resources held by a process and allocating them to another process to resolve circular waits or unsafe states.
